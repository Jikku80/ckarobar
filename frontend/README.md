# DentalDB Mobile — Phase 1

Flutter app (Android + iOS from one codebase) for the DentalDB clinic
management system. This is **Phase 1 of the mobile build** — see "Roadmap"
below for what's next.

## What's in Phase 1

- Project scaffold (Riverpod + go_router + Dio)
- **Auth**: login, cookie-based session persisted across app restarts,
  silent token refresh every 12 minutes (mirrors `AuthProvider.tsx`),
  auto-redirect to login on session expiry
- **RBAC**: permissions pulled from `/rbac/me/permissions`, nav items and
  quick-links gated exactly like `lib/permissions.ts` / `NAV_ITEMS`
- **Branch switching**: same selection rules as `auth.store.ts`
  (single-branch non-owners locked to their branch; locked/inactive
  branches can't be made active)
- Dashboard shell (drawer nav, role-aware) + placeholder screens for
  modules landing in later phases, so the nav already matches the web app

Not built yet (all show a "coming soon" screen for now): Patients,
Appointments, Billing, Staff, Branches admin, Roles, Inventory, Reports,
Attendance, Leave, Settings. These are next up per your selected scope
(Patients + Appointments, then Admin: Users/Branches/RBAC/Reports/Inventory).

## One-time setup (do this before opening the project)

This zip contains only the Dart source (`lib/`) and `pubspec.yaml` — not
the generated Android/iOS platform folders, since those need to be
generated by your local Flutter SDK/toolchain version. To turn this into a
runnable project:

```bash
# 1. Unzip, then from inside the project folder:
flutter create --project-name dentaldb_mobile --org com.yourclinic .
# This generates android/, ios/, and other platform folders WITHOUT
# touching the lib/ and pubspec.yaml already in this zip (it only fills
# in what's missing).

# 2. Install dependencies
flutter pub get

# 3. Point at your backend (see "Configuring the API URL" below), then run
flutter run
```

If `flutter create .` complains the directory isn't empty, that's fine —
it only adds the platform folders it doesn't find; it won't overwrite
`lib/` or `pubspec.yaml`.

## Configuring the API URL

`lib/core/config.dart` mirrors the web app's `NEXT_PUBLIC_API_URL`
convention exactly (base origin, no `/api/v1` suffix — that's appended
once, in code).

- **Production build** defaults to `https://app.clinickarobar.com` (same
  origin the web dashboard uses).
- **Debug build** defaults to `http://10.0.2.2:4000` (Android emulator's
  alias for your host machine's `localhost:4000`, matching the backend's
  default port).

Override either at run time without editing code:

```bash
flutter run --dart-define=API_BASE_URL=https://your-backend.example.com
```

- Android emulator → backend on your machine: use `http://10.0.2.2:PORT`
- iOS simulator → backend on your machine: `http://localhost:PORT` works
- Physical device (either OS): use your machine's LAN IP, e.g.
  `http://192.168.1.23:4000`, and make sure the device is on the same
  network and your backend's CORS allows that origin.

## Why cookies work the same as the web app

The backend sets HttpOnly auth cookies on `/auth/login`. Flutter can't read
those in Dart code (same as the browser — that's the point of HttpOnly),
so instead of trying to extract a token, this app uses a `PersistCookieJar`
(`dio_cookie_manager` + `cookie_jar`) that stores and resends cookies
automatically on every request, and persists them to disk so a session
survives an app restart — functionally identical to what the browser does
for the web app's `withCredentials: true` requests.

`lib/core/api_client.dart` also mirrors `lib/api.ts`'s 401-triggers-refresh-
then-retry-once interceptor, including queueing concurrent requests behind
a single in-flight `/auth/refresh` call.
